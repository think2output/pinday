# PinDay 프로젝트 회고 — 기능을 잇고, 피드백으로 다시 설계한 과정

작성일: 2026-10-25 · 팀 공유 및 포트폴리오 설명용  
조사 기준: 구현 `a8418a7`, 원격 main `a973334`(PR #21 병합), 비교 문서 `9b46811`. 이번 작업은 기록 조사와 문서 작성이며 기능 수정·병합·운영 배포를 수행하지 않는다.

## 1. 이 프로젝트에서 해결하려던 문제

PinDay는 부산 여행자가 장소 정보, 지도, 일정, 이동 수단, 장소 설명을 여러 곳에서 찾아야 하는 문제에서 출발했다. 장소를 많이 보여주는 것에 더해, **직접 고른 장소가 왜 의미 있는지 이해하고 그 이야기를 여행 계획으로 가져오는 경험**을 만들려 했다. 이 문제 정의는 [기획서 1·2·8장](기획서.md)에 기록된 기획 가설이다. 실제 이용자 조사로 문제의 크기나 개선 효과를 측정한 기록은 확인 불가다.

서비스 방향은 “AI가 여행을 대신 짜주기”보다 “내가 고르고 가서 더 깊이 즐기기”였다. 그래서 지역을 누르고, 이야기를 살피고, 마음에 드는 장소를 담고, 날짜를 정하는 행동을 사용자의 선택으로 남겼다. AI 도슨트도 빈 부분을 그럴듯하게 채우기보다 근거가 없다고 표시하는 원칙을 택했다. [DECISIONS의 서비스·AI 도슨트 결정](DECISIONS.md)

시각적 출발점은 PM이 제안한 두 가지 핀이었다. 지도에 꽂는 핀과 전시실에서 대상을 비추는 핀 조명을 겹쳐, “부산이라는 전시실에서 내가 고른 곳의 이야기가 켜지는” 경험으로 풀었다. 이후 지도 윤곽, 카드, 랜덤 뽑기, 취향 테스트 수정은 이 방향이 실제 화면에서도 느껴지는지를 확인하는 과정이었다. [디자인 탐색 기록](design/README.md), 대화 L1

## 2. 기존 팀 작업과 이번 구현의 경계

비교 대상은 사용자가 지정한 [이전 PinDay](https://pinday-web.vercel.app/)와 [현재 첫 배포 주소](https://pinday-five.vercel.app/)다. 이전 소스는 [map-5의 고정 커밋](https://github.com/ohzoohzo/map-5/tree/ba62012f9768bc6d785ce407bf8b8a1ae96e6b9f)을 기준으로 확인했다. 이 저장소 README에는 이전 배포 도메인과 화면별 담당이 기록돼 있다. 다만 이전 운영 배포와 이 소스의 정확한 커밋 일치 여부는 확인 불가다.

**탐색·후보함·일정·취향 테스트·랜덤 뽑기·날씨 대안·이동 경로·근거 기반 도슨트는 기존 서비스에도 있었다.** 이전 코드에서 공유 여행 저장소 사용, 취향 결과 저장과 탐색 연결, 3회 랜덤 뽑기와 후보 담기, 근거 밖 사실을 쓰지 않도록 한 도슨트 생성 지침을 확인했다. 이를 이번에 처음 발명하거나 처음 연결한 기능으로 설명하면 기존 팀 기여를 지우게 된다.

이번 저장소는 Next.js 한 프로젝트 안에서 화면과 서버 기능을 구현하고, 기존 개념을 다음과 같이 재구성·보강했다.

- 홈의 실제 부산 경계 지도, 핀·조명, 승인된 이야기에서 상세로 이어지는 진입 흐름.
- 도슨트의 사전 생성, 사용할 근거 문단 제한, 문장 대조, PM 승인과 공개 조건 분리.
- 랜덤 결과를 이야기 카드 선택으로 전환하고, 취향 결과의 대표 코스를 명시적으로 날짜에 추가.
- 날씨 상태를 구분하는 안내, 한 장소씩 대안을 결정하는 화면, 구간별 이동 수단과 PC 가로 동선.
- 이번 저장소의 공통 여행 규칙과 화면별 예외·회귀 검증. 기존 서비스의 모든 규칙이 없었다는 뜻은 아니다.

반대로 자동차 경로와 최근 소식 등 기존 코드에 있던 부분을 현재 범위에 모두 이어오지는 않았다. 기능 수가 모든 면에서 늘어난 프로젝트로 평가하지 않는다. 기존 근거 기반 도슨트 설계는 기획서에 명근 님의 기여를 계승한다고 명시돼 있다. 이번 PM 피드백·선택과 에이전트의 구현·검증도 구분해 서술한다. 세부 비교는 [SERVICE_EVOLUTION](SERVICE_EVOLUTION.md), 기존 코드 근거는 부록 B를 참고한다.

## 3. 기록을 해석하는 기준

이 문서의 **PM 피드백**은 읽을 수 있는 사용자 대화 또는 PM의 말로 명시된 결정·QA 기록을 뜻한다. **에이전트 판단**은 그 요청에 대해 제안·구현한 방법이다. 대화 원문이 없는 경우에는 “문서 기록 기준”이라고 썼다. 구현 결과에서 과거 사용자의 발언을 역으로 만들어내지 않았다.

완료 상태는 네 가지로 나눈다.

| 상태 | 이 문서에서 뜻하는 것 | 뜻하지 않는 것 |
| --- | --- | --- |
| 소스 구현 | 코드·데이터가 특정 커밋에 존재 | 화면 검증·운영 성공 |
| 검증 완료 | 명시한 환경·폭·입력·응답에서 확인 | 모든 기기·모든 장소에서 정상 |
| main 병합 | GitHub PR 상태와 원격 Git 이력으로 확인 | 운영 주소에 해당 코드가 반영됨 |
| 운영 배포 | 운영 주소·배포 커밋·실제 동작의 확인 범위 | 미리보기 Ready 또는 HTTP 200만으로 전체 QA 통과 |

아래 사례의 화면 검증은 별도 표기가 없으면 **당시 에이전트가 별도 Chrome 프로필에서 수행한 로컬 기록**이다. 이번 회고 작성 중 기능 화면 QA나 유료 API 호출을 다시 실행한 결과가 아니다. 390px은 휴대폰 폭 모의 환경이며 실제 휴대폰 검증과 다르다. 과거 QA 문서 상단·하단에는 작성 당시 상태가 함께 남아 있어 최신 결정과 커밋을 대조했다.

## 4. 주요 사례

### 4-1. 핀 조명 디자인: 레퍼런스를 장식으로 옮겼다가 방향을 다시 잡다

**의도** → 부산 지도와 도슨트를 하나의 시각적 콘셉트로 묶으려 했다. PM은 명조와 과한 화려함을 피하면서 고딕 글꼴로 큐레이션 느낌을 원했다. 마우스를 따라 정면에서 비추는 조명도 PM의 제안이었다.

**문제/피드백** → 초기 시안에는 따뜻한 종이색, 구분선, 긴 카피, 영문 라벨, 형광펜 표현, 둥근 카드 등이 늘어났다. PM은 “의미없는 짝대기가 많”아 인위적으로 보이고, 보내준 레퍼런스의 느낌이 살지 않는다고 지적했다. 좋아한 것은 움직이는 조명과 전시 벽의 사진 구성이었는데 에이전트가 레퍼런스의 부드러움을 둥근 형태·파스텔로 해석한 것이 어긋났다. 대화 L1

**판단과 변경** → 여러 요소를 계속 얹는 대신 A·B·C 시안을 비교했고 PM이 C ‘어두운 전시실’을 선택했다. 흰 페이지, 먹색 상단, 노란 조명, 각진 모서리, Wanted Sans/Pretendard로 기준을 정했다. PM은 윤슬 효과를 본 뒤 제거하고 먹색을 유지하도록 선택했다. 사진은 이용 조건을 지키기 위해 기울이지 않고 자체 장식만 기울였다. 대화 L2

**검증 결과** → 선택 시안 원본과 디자인 값·글꼴·라이선스를 저장하고 실제 홈에 반영했다. 이는 디자인 의사결정과 구현의 근거이며 사용성 향상의 수치 증거는 아니다. [시안 C 휴대폰](design/home-c-mobile.dc.html) · [PC](design/home-c-desktop.dc.html), [결정 `7d7ea37`](https://github.com/think2output/pinday/commit/7d7ea37), [구현 `54ccf09`](https://github.com/think2output/pinday/commit/54ccf09), [PR #7](https://github.com/think2output/pinday/pull/7)

**남은 한계** → 전체 화면의 디자인 확정과 홈 첫 문구는 아직 남아 있다. 시안에 대한 선호 확인을 전체 서비스의 최종 승인으로 넓혀 해석하지 않는다.

### 4-2. 블록형·임의 윤곽 지도에서 실제 부산 행정 경계로

**의도** → 초기 기획은 중구·동구처럼 작은 구도 휴대폰에서 쉽게 누르도록 비슷한 크기의 16개 블록을 쓰는 것이었다. 명소 선화로 부산다움을 더하려 했다. 이때의 선택 편의와 이후의 실제 지형 보존은 서로 다른 우선순위였다.

**문제/피드백** → PM이 남은 명소 그림을 요청하면서 “부산 윤곽이 느껴지는 지도 조각 안에 명소 그림”이라고 명확히 했다. 에이전트의 임의 다각형 시안에 대해서는 “지도윤곽 최악인데”라고 지적하고 실제 부산 형태가 보이는 참고 이미지를 제시했다. 문제는 그림 13개 부족만이 아니라 지도의 형태를 해석한 방식이었다. 대화 C4, 10-25 15:48~16:05

**판단과 변경** → 작은 구를 크게 왜곡하는 대신 실제 해안선·섬·상대 크기를 보존했다. 에이전트는 SGIS 2020 자료를 SVG로 변환한 StatGarten 저장소의 고정 커밋을 사용하고 원본 path 16개를 추출했다. 상업용 참고 이미지를 그대로 복사하지 않고 출처·MIT 원문을 보관했다. 오목한 구의 이름표가 다른 구로 빠지는 것을 피하도록 구 내부의 여유 공간을 탐색해 배치했다.

**검증 결과** → 당시 390/1440px에서 실제 좌표로 16개 구를 클릭·터치하고 선택·해제·새로고침 유지·가로 넘침을 확인했다. 선화는 16개를 준비했다. 소스는 [`mapLayout.ts`](../src/app/_home/mapLayout.ts), [`BusanMap.tsx`](../src/app/_home/BusanMap.tsx), [지도 자료·라이선스](../data/maps/README.md). [커밋 `869aa71`](https://github.com/think2output/pinday/commit/869aa71), [HOME_QA ‘실제 경계 지도’](HOME_QA.md)

**남은 한계** → 2020년 경계이므로 최신 법적 경계를 보증하지 않는다. 초기 임의 윤곽은 최종 캡처로 덮어써져 정확한 중간 모습은 현 디자인 폴더만으로 복원할 수 없다. PM이 거부한 사실은 대화·결정 기록에서 확인된다.

### 4-3. 작은 구의 아이콘 생략, 드롭다운·확대 제거와 긴 스크롤

**의도** → 실제 지형을 쓰면서도 작은 구를 고를 수 있게 이름 드롭다운과 확대를 보완 수단으로 넣었다. 처음에는 확대하면 작은 구의 아이콘도 보이게 했다. 이는 에이전트가 선택 편의를 보완하려 택한 접근이었다.

**문제/피드백** → PM은 구가 작으면 아이콘을 빼도 되며 드롭다운은 필요 없다고 했다. 이후 확대도 필요 없고 그 때문에 화면의 스크롤이 너무 길어진다고 지적했다. 모든 그림과 보조 조작을 유지하는 것이 첫 화면 경험에 도움이 되지 않았다. 대화 C4, 16:34·16:48

**판단과 변경** → 넓은 9개 구만 그림, 좁은 7개 구는 이름만 남겼다. 드롭다운을 없애고 경계 자체에 Tab/Enter/Space 선택을 제공했다. 다음 수정에서 확대·축소·지도 내부 스크롤도 제거하고, PC 지도 최대 폭 640→512px 및 상단·이야기 앞 여백을 줄였다. 지도 출처는 푸터로 옮겼다. 앞서 추가한 확대를 나중에 제거한 순서를 생략하지 않는다.

**검증 결과** → 390/1440px의 최종 지도에서 16개 경계 조작·키보드 선택·아이콘 9개·보조 조작 제거·저장 유지·가로 넘침 없음을 확인했다. 기본 상태 이야기 시작 위치는 390px에서 1,094→903px, 1440px에서 1,134→756px이었다. 이는 같은 QA의 화면 위치 측정이며 이탈률이나 탐색 시간 개선 수치가 아니다. [커밋 `8f27575`](https://github.com/think2output/pinday/commit/8f27575) → [`37dbde6`](https://github.com/think2output/pinday/commit/37dbde6), [HOME_QA](HOME_QA.md), [최종 휴대폰 화면](design/home-map/home-stories-390.png)

**남은 한계** → 실제 작은 구의 터치 면적은 44px보다 작을 수 있다. 키보드 접근은 보완했지만 “모든 구가 44px 이상”이라는 초기 수용 기준을 충족했다고 쓸 수 없다. 실제 휴대폰에서 작은 구 선택의 편의는 후속 확인이 필요하다. `map-zoom-*` 사진은 과거 확대 버전이다.

### 4-4. 클릭 시 흰 테두리와 핀·물결·마우스 조명

**의도** → 지역을 고르면 핀이 떨어지고 조명이 켜져 선택을 알아볼 수 있게 하려 했다. PM은 마우스를 따라오는 빛의 색감과 핀의 낙하 감각을 강화해 달라고 했다.

**문제/피드백** → 클릭 뒤 흰 사각 테두리가 생겼고, 핀의 위치·움직임도 PM이 원한 “구 이름 위에 툭 떨어지고 물결이 퍼지는” 모습과 달랐다. 원인은 경계 요소의 브라우저 포커스 outline과 별도로 다듬어야 할 핀 좌표·연출이었다. 대화 C4, 16:34·16:43 및 현재 CSS/QA

**판단과 변경** → 마우스 클릭의 사각 outline을 제거하되 키보드 포커스는 실제 구 경계의 노란 선으로 남겼다. 핀 가로 중심을 구 이름과 맞추고 이름 바로 위로 이동·확대했다. 새 선택에 0.62초 수직 낙하·작은 튕김, 발끝에서 0.9초 두 겹 물결을 더했다. 조명은 화면 포인터 좌표를 지도 SVG 좌표로 바꿔 지도 표면과 주변에 함께 표시했다. 저장된 핀을 다시 열 때는 낙하를 재생하지 않고 움직임 줄이기에서는 즉시 표시한다.

### 4-15. 이동 경로: 중단된 작업 복구, 반복 목록 재설계, 실제 응답 확인

**의도** → 일정의 점선을 실제 길찾기와 구분하고 구간별 이동·환승을 이해하게 하려 했다. 기존에도 이동 경로가 있었으며 이번에는 대중교통·도보에 범위를 집중했다.

**문제/피드백** → 다른 AI가 커밋·인계 없이 멈췄다는 사용자 보고로 재개했다. PM은 기존 변경을 지우지 말고 먼저 상황을 확인하고 WIP 커밋으로 보존하라고 요청했다. 또 ‘하루 1,000건 무료’처럼 확인하지 않은 문구를 빼도록 했다. 기능 연결 후에는 구간마다 큰 상자가 만드는 빈 공간, PC의 반복 세로 목록이 불편하다고 두 차례 지적했다. **앞 에이전트가 멈춘 원인은 확인 불가**다. 대화 C3, 12:03~12:29

**판단과 변경** → 먼저 기존 미완성 변경을 `wip(route)`로 저장했다. 자동차는 보류하고 대중교통·도보를 구간별로 선택하며 환승은 탈 것마다 나눴다. 요약 행으로 줄이는 첫 수정 뒤에도 PM의 재검토가 이어져 PC 가로 동선 A와 지도 선택 B 시안을 비교했다. 에이전트는 장소가 많거나 지도 실패 시에도 구간 선택을 유지할 수 있는 A를 권했고 PM이 채택했다. 구현·모의 QA 뒤 사용자 제공 앱 사용량 표를 확인하고 최소 실응답 검증을 따로 진행했다.

**검증 결과** → PC A안은 390/1050/1440px·12곳 마지막 구간·수단 독립 유지·지도 실패·키보드·화면 크기 전환을 시험 응답으로 검증했다. 이후 **10-25 12:45 KST 감천→송도**를 실제 서버 응답으로 확인했다. 대중교통 28분·61번 버스, 도보 62분·3,769m·두 수단 HTTP 200은 당시 결과다. 로컬 API 요청은 2건이며 서버 캐시를 분리 측정하지 않아 외부 호출은 0~2건으로만 기록했다. [WIP `7d03eef`](https://github.com/think2output/pinday/commit/7d03eef) → [PC `12de57c`](https://github.com/think2output/pinday/commit/12de57c) → [실응답 `b39f01d`](https://github.com/think2output/pinday/commit/b39f01d), [PR #16](https://github.com/think2output/pinday/pull/16)·[PR #17](https://github.com/think2output/pinday/pull/17), [시안 판단](design/route-desktop-ux/README.md), [ROUTE_QA](ROUTE_QA.md), [실응답 사진](design/route-ux/live-transit-390.png)

**남은 한계** → 한 구간·두 수단의 실제 응답 확인을 모든 경로의 정확성으로 확대할 수 없다. 실제 휴대폰에서 카카오맵 앱 전환은 미확인이다. 사용량 표의 1,000은 당시 해당 앱의 일간 쿼터 스냅샷이며 무료 정책의 증거가 아니다. 자동차와 비용 정책은 후속 확인이다. 시안 A/B의 같은 이름도 단계가 다르므로 초기 API/링크 비교와 이후 PC 구조 비교를 구분한다.

### 4-16. Vercel 첫 배포와 카카오 지도 도메인 설정

**의도** → 다음 기능을 늘리기 전에 실제 접속 주소에서 확인하자는 PM의 선택으로 첫 배포를 진행했다.

**문제/피드백** → PM은 10-25 15:40에 배포 성공 주소를 공유했지만 지도는 뜨지 않는다고 보고했다. 로컬에서도 이전에 `127.0.0.1`에서는 SDK 오류가 나고 `localhost`에서는 정상 표시된 사례가 있었다. 화면 소스가 있다는 것과 해당 주소에서 외부 지도 서비스가 허용되는 것은 다른 조건이었다. 대화 C2·C4

**판단과 변경** → 카카오 JavaScript SDK 도메인에 첫 배포 주소를 추가하고 localhost 등록은 유지하도록 안내했다. 서버 키를 클라이언트에 옮기는 방식은 쓰지 않았다. 이후 PM이 “뜬다”라고 지도 표시를 확인했다. 이는 도메인 등록 문제를 뒷받침하는 해결 경과지만 에이전트가 카카오 설정 화면 자체를 직접 확인한 기록은 아니다.

**검증 결과** → 당시 에이전트는 홈·탐색 HTTP 200을 확인했고 배포 성공과 지도 표시는 사용자 보고로 기록했다. [커밋 `582924d`](https://github.com/think2output/pinday/commit/582924d), [PR #20](https://github.com/think2output/pinday/pull/20). 이번 조사에서는 PR #21의 [Vercel 봇 댓글](https://github.com/think2output/pinday/pull/21#issuecomment-6395584469)에 브랜치 Preview Ready가 있는 것도 확인했다. **미리보기 성공과 운영 주소의 최신 반영은 구분한다.**

**남은 한계** → 운영 배포의 정확한 소스 커밋·환경변수 등록 목록·자동 배포 설정·전체 여행 흐름은 확인 불가다. 이번 조사에서 웹 읽기 도구는 두 운영 URL에 접근하지 못했다. 대체 HTTP 읽기로 양쪽 모두 200 응답과 PinDay 문서 제목은 확인했지만, 자바스크립트 실행 후의 최신 화면·지도·전체 흐름은 재확인하지 못했다. 당시의 성공 기록을 오늘 새로 수행한 운영 QA로 적지 않는다.

### 4-17. 에이전트 인계: 오래된 상태와 넓은 ‘확인 완료’를 바로잡다

**의도** → 여러 에이전트가 번갈아 작업해도 이전 결정과 여행 데이터를 보존하고 바로 이어받게 하려 했다. 한 번에 한 에이전트만 작업하는 규칙을 유지했다.

**문제/피드백** → 중단된 경로 작업 외에도 QA에 구현 전 안내가 남거나, 이미 병합된 PR을 미생성·미병합으로 적거나, 상세 사진만 확인하고 도슨트 전체를 확인한 것처럼 읽히는 문제가 생겼다. 기존 PinDay 비교를 요청했을 때 에이전트가 비교 대상을 다시 물어 PM이 기존 주소를 재지정한 일도 있었다. 대화 C3·C4, 커밋 차이

**판단과 변경** → HANDOFF를 현재 상태 중심으로 다시 쓰고 ‘다음 에이전트에게’를 앞에 두었다. 과거 QA를 지우는 대신 이후 변경을 표시하고 실제 원격 main·PR 상태로 바로잡았다. 사진 확인은 홈/목록/상세, 경로는 시안/시험 응답/실응답, 배포는 사용자 보고/HTTP 응답/운영 전체 흐름으로 나눠 기록했다. 중간 결과는 작은 커밋으로 보존하고 막힌 이유도 인계했다.

**검증 결과** → 세션 정리 [`cfad062`](https://github.com/think2output/pinday/commit/cfad062)·[PR #13](https://github.com/think2output/pinday/pull/13), 배포 인계 `582924d`, 목록 재검증 `a8418a7`, 비교·병합 정정 [`9b46811`](https://github.com/think2output/pinday/commit/9b46811)의 실제 문서 차이를 확인했다. 이번에도 원격을 가져와 main `a973334`와 PR #21 merged=true를 대조했다. 같은 상태를 적은 옛 문서보다 실제 Git·PR 확인을 우선했다.

**남은 한계** → 문서 곳곳의 과거 문구를 전부 최신으로 바꾼 것은 아니다. 예를 들어 초안 검수 문서의 미체크 항목과 QA의 ‘다음 구현’ 문장은 작성 시점 기록이다. 모든 대화·비공개 캔버스·설정 화면을 복원할 수 없으며, 여러 에이전트의 제안과 실제 사용자 승인 사이가 문서만으로 완전히 드러나지 않는 부분은 남는다.

## 7. 이번 과정에서 배운 것과 포트폴리오에 설명할 사례

기능 동작과 사용자 경험을 같은 완료 기준으로 취급하면 재작업이 생긴다. 홈 여행 카드는 초기화·복구 테스트를 통과해도 화면에서는 채택되지 않았다. 랜덤 뽑기도 결과가 나오기만 해서는 서비스가 원한 ‘직접 고르는 재미’를 전달하지 못했다. 이번 과정에서는 PM이 화면을 보고 문제를 좁히고, 에이전트가 시안·구현·검증으로 구체화하는 반복이 필요했다.

또한 정확한 데이터가 많다는 것과 공개할 수 있는 이야기가 많다는 것은 다르다. 자동 충분 후보를 191곳에서 83곳으로 줄이고 실제 공개를 6곳으로 제한한 것은 콘텐츠 확대보다 사용 범위를 먼저 정한 판단이었다. 공개 수를 성공 지표처럼 부풀리기보다 어떤 문장을 왜 쓸 수 있는지 설명하는 것이 포트폴리오에서 더 설득력 있다.

다음은 팀 기여를 밝힌 뒤 사용할 수 있는 설명 초안이다. 개인이 모든 코드를 직접 작성했다거나 기존 기능을 새로 발명한 것처럼 바꾸지 않는다.

1. **실제 부산 지도와 화면 간결성의 충돌을 조정한 사례**  
   “기존 팀 프로젝트를 발전시키면서 PM으로 지도 방향과 화면 피드백을 맡았다. 선택 편의 중심의 블록 지도와 임의 윤곽이 의도와 달라 실제 경계를 쓰도록 방향을 정했다. 이후 작은 구의 아이콘과 보조 조작을 줄이고, 에이전트가 실제 경계·키보드 조작·핀 연출을 구현·검증했다. 화면이 짧아진 것은 QA 위치 측정으로 확인했으며 실제 이용 시간 개선은 아직 측정하지 않았다.”

2. **근거 기반 도슨트의 공개 절차를 구체화한 사례**  
   “팀의 기존 근거 기반 해설 설계를 계승해 사전 검수·승인 흐름을 정리했다. 에이전트가 출처 충돌과 단순 언급을 걸러 사용할 문단을 제한하고 문장을 대조했으며, PM은 요약 보고를 보고 공개 범위를 승인했다. 근거 408곳·자동 후보 83곳·생성 7곳·공개 6곳을 구분해, 수집량을 공개 품질로 오해하지 않게 했다.”

3. **긴 목록을 사용자의 결정 단위로 바꾼 사례**  
   “날씨 대안과 이동 경로에서 정보가 늘어날수록 선택이 어려워지는 화면을 지적했다. 대안을 전부 나열하는 대신 한 장소의 교체를 결정하게 하고, PC 경로는 하루 동선에서 한 구간을 선택하도록 시안을 비교·채택했다. 에이전트는 기존 일정 보존과 오류 상황을 검사하고, 경로는 시험 응답 QA 뒤 최소 실제 응답 확인을 분리했다.”

4. **‘확인 완료’의 범위를 바로잡은 사례**  
   “도슨트 상세 사진 수정 뒤 목록의 크기 문제를 다시 발견했다. 실제 메뉴로 들어가는 검증을 추가하고 홈·목록·상세를 별도 범위로 기록했다. 에이전트 인계에도 코드 구현·QA·main 병합·운영 배포를 나눠 다음 담당자가 미완료 검증을 이어받도록 했다.”

성과로 말할 수 있는 것은 구현과 특정 검증의 결과다. 계획 시간 감소, 만족도 상승, 이탈률 개선, 정확도 100%, 운영 비용 절감률은 측정 자료가 없어 **확인 불가**다.
